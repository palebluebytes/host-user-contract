A NixOS interface specification  ·  palebluebytes/host-user-contract

Any host
can enable
any user.

This repository is not a host configuration and not a user configuration. It is the negotiated interface between them — a shared schema, a host-invariant way of turning a person into an account, and the derivation logic both sides agree on. It depends on nothing but nixpkgs lib: no home-manager, no packages.

HOST — the machine USER — the person CONTRACT — neither
01

What this repo actually does

The north star, and the problem underneath it

Imagine a machine sitting in a room. Somebody walks up to it, types a flake URL, a username and a password — and their machine is there. Their desktop, their dotfiles, their shell, their editor. Nothing about that person was declared on that machine in advance. They were a stranger to it thirty seconds ago.

That is the north star, and everything else in this repository is the build-time version of the same handshake. When the walk-up path and the declarative path disagree about what a machine can run, the walk-up path is what the design is answerable to — not the other way round.

The problem it solves

In an ordinary NixOS fleet, a host's configuration owns its users: their groups, their passwords, their home content, all tangled into configuration.nix. Move a person to a second machine and you copy, edit and drift. Give a person a machine to log into and you must first change that machine's source and rebuild it.

This contract cuts that knot by splitting the question into two halves that never touch:

The user answers

Who am I, and what session shapes do I run in?

A public identity (identity.json) and a declaration (user.nix) naming the modes they run in and the home-manager module to build for each. Nothing about privilege. Nothing about any particular machine.

The host answers

What can this box run, and what may this person do on it?

Two different kinds of statement, deliberately kept apart: contract.modes once for the machine, and an affordance at each bind, on the line that already names the person.

The distinction the whole design rests on A display is a fact about the hardware; sudo is a judgement about a person. A headless server does not decline to give Ada a desktop — it cannot run one. Incapacity is not a ban. That is why the two live in different places and are never negotiated against each other.
02

The two parties and the seam

Two repositories that know nothing of each other's internals

In practice there are two consumer repositories. A users repo builds each person's home ahead of time and publishes it. A host repo binds whichever of those people it is willing to confer something to. The contract sits between, and is imported by both.

Everything is built ahead of time

A home is a sealed derivation. It is built by the users repo, on the users repo's own terms, before any host has been asked about it. This is the single most consequential fact in the design: a host can only pick a home, never adjust one. Content cannot be injected into something already built.

Which is why the two words the rest of this document turns on are different words. A mode is the part a bind cannot change — it is baked in. A grant is the part a bind can still confer, at activation, on the account rather than on the home.

03

Two vocabularies that touch nowhere

modes.nix and features.nix — the two registries

The contract has exactly two registries, and each is the single source of truth for one vocabulary. Every other surface in the repository — a user's option set, a host's enum, the greeter's offer, the group list on an account — is a projection of one of them. Keys cannot drift, because there is only one set of keys.

The mode registry — modes.nix

ModeIsGroups it carriesNeeds a display?Its own parameters
cli FLOOR A terminal-only session. nonenonone
gui A graphical desktop session. input uinput plugdev dialout yes → contract.display.enabled desktop

The floor is implicit and unexcludable. cli carries the floor flag, which means every host runs it, nobody declares it, and there is no spelling anywhere that removes it. Exactly one mode may be the floor; zero or two is a named error. Modes are mutually exclusive — a home is built for exactly one — which is why N modes yield at most N homes per user rather than 2N.

The feature registry — features.nix

FeatureConfersGroupsNotes
sudoAdministrative access, and nothing more. wheel The minimal privileged grant. A user can never obtain wheel by declaring it — an identity cannot name a group at all.
containersPrivileged container-runtime access. docker podman Both are root-equivalent. Atomic, so “containers without sudo” is expressible.
virtualizationRunning VMs. disk qemu-libvirtd libvirtd A power somebody decided you should have, not a property of the machine.
nix-daemonTalking to the Nix daemon socket. nix-users Without it a user is daemon-restricted: they cannot build derivations, install packages, or add store paths beyond what the host activated for them.
Atomic

Each feature confers exactly one concern's groups. A host composes them (sudo + containers) rather than granting one coarse role.

Parameterless

A feature is a boolean. Anything that would need a parameter is not a feature — a desktop name is a property of the graphical session, so it lives on the mode.

The safe set is empty

The “safe set” is derived, not listed: the features declaring no privileged groups. Today that is none of them, so a walk-up stranger receives a session, and no power at all.

04

The user’s side — every option

Two files, and that is the whole of what a person says

A user is a directory. Everything a person can say to this contract is in it, and the surface is deliberately tiny: a user names who they are and which session shapes they run in. There is no third thing.

users/ada/user.nix — the declaration
# The WHOLE of what a user says.
{
  contract.cli = {
    enable        = true;
    configuration = ./home.nix;
  };
  contract.gui = {
    enable        = true;
    configuration = ./home.nix;   # or ./gui.nix, if the session needs different content
    desktop       = "plasma";     # a free-form name the seat maps to a real desktop
  };
}

The declaration schema

This is a projection of the mode registry: one submodule per mode, generated. A contract that gains a mode gains its declaration with no edit anywhere, and a user naming a mode the contract does not have is an eval error in the user's own repo rather than a user nothing can bind.

OptionTypeDefaultWhat it means
contract.<mode>.enableboolfalse Whether this user runs in this session shape. Nothing defaults to enabled — a default would decide what a user is without the user having said anything. Enabling none is a named error at bake time.
contract.<mode>.configurationdeferredModule{ } The home-manager module built for this mode. Deferred, so reading which modes a user runs in never forces the home. Empty is legitimate — a service account or a break-glass admin still gets an account and the contract's home baseline.
contract.gui.desktopstr"" The gui mode's own parameter. A free-form, DE-agnostic name that travels with the user — published in the binding index as modeParams.gui.desktop, so the seat maps it to a real desktop without opening a home. An un-offered or empty name degrades to the seat's default. It never names a package.
Why two modes may name the same file That is the common case — a home that does not depend on the session. Point them at different modules only when the content genuinely differs (a sway config has no terminal equivalent), which is exactly why a mode is a mode: content cannot be injected into a sealed derivation, so those are two derivations rather than one home with a switch in it. A user whose two modes build identical homes is conforming, not misconfigured.

The identity — users/ada/identity.json

Inert data, not Nix. That is load-bearing: a greeter authenticates against this file before evaluating a single line of the user's Nix. An identity describes a person, never their powers — every field is either descriptive or a login credential, and nothing in it reaches host state on its own.

users/ada/identity.json — the full form
{
  "name":           "Ada Reference",
  "email":          "ada@example.invalid",
  "username":       "ada",
  "hashedPassword": "$y$j9T$A5WpCOX3TaFRciO.ILZsD1$pHwIEiJI6anN/oQw…",
  "sshKey":         "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIADAexamplekeyada",
  "trustedKeys":    []
}
FieldTypeRequiredBecomes
usernamestrrequiredThe one required field. The system account name — the one value nothing downstream can invent. It must equal the index key, or the producer refuses to publish.
namestr""The account's GECOS / description.
emailstr""Descriptive; read by home modules through contract.identity.
hashedPasswordstr""The login credential, carried verbatim. A one-way hash — the only secret this contract touches.
sshKeystr""The primary authorized key (dropped when empty).

An unknown key is a loud error, and a missing required field is a loud error — never a silently-wrong account. Note what the schema does not contain: any notion of what this account may do. It used to carry extraGroups, and that was the one exception — a user wrote group names into their own public record and a host materialised them, filtered by a deny-list. On the greeter path that meant a stranger could put themselves in a group by editing their own file. It is gone.

What a home is handed

Home optionTypeNotes
contract.identity.*the identity schema above read-only A home holds its identity — it neither loads it nor authors it, so git.userName and friends read one resolved value instead of every home re-parsing JSON. A second definition is an eval error, not a merge.
…and that is the whole of it. The contract composes no content into a home — the mode's own parameters (gui.desktop) are published in the binding index instead, where a seat reads them without opening anything.
The user's one refusal

A user cannot ask for a feature and cannot veto one — which powers an account holds is the host's decision alone, because a user-side veto would be a second authority over one value with nothing forcing the two to agree. But the refusal a user actually needs — never give me a desktop — is already expressible: don't enable the gui mode, and no host can select a graphical home that was never built.

Confinement — what a home cannot say

A user's home is a home-manager module with no system channel. users.users, security.sudo, boot.*, sops.* are unexpressible, not merely rejected. Privilege escalation is impossible because the vocabulary to ask for it does not exist. The check kit ships a proof of this that a consumer runs against its real module set, positive control included.

05

The host’s side — every option

One statement about the machine, one per person

A host says two different kinds of thing, and keeping them apart is the shape of the whole design. Everything the contract puts on a host lives under contract.* — there is one option prefix and none per party.

hosts/desk.nix — a seat
{ contract, users, ... }:
{
  # WHAT THIS MACHINE IS — declared once, for the box.
  contract.modes = [ "gui" ];

  imports = [
    contract.nixosModules.default

    # WHAT EACH PERSON MAY DO — declared at the bind, which already names them.
    (contract.lib.bindContractUsers {
      source = users;
      users = {
        ada             = { };            # nothing afforded — the MACHINE gives her the desktop
        cleo.containers = true;
        admin.sudo      = true;
      };
    })
  ];
}

A. What the machine is

OptionTypeDefaultWhat it means
contract.modeslistOf enum [ cli gui ][ ] The session shapes this machine can run, beyond the floor. Fail-closed: a host that says nothing runs cli and only cli. It is a set, not a sequence — [ "gui" ], [ "gui" "cli" ] and [ "cli" "gui" ] are one declaration, and there is no spelling that excludes the floor.
contract.exposedbool (enableOption)false A plain fact an operator records — this box is agent-facing / internet-exposed. The contract enforces nothing on it; it is available for a host's own policy and is one of the three hostFacts a home is told.
contract.packagePolicy.
allowedPrograms		listOf str[ ] After activation, the host replaces ~/.nix-profile with the intersection of this list and the user's published package manifest. Each name resolves to pkgs.<name> from the host's pin; unknown names are dropped. Empty means no policy at all. Meaningful mainly for a daemon-restricted user, for whom that profile is the only store they can reach.
contract.display.enabledboolread-only · derived Does any mode this machine runs need a shared display surface? Derived from the display flag in the mode registry — never by naming gui. It follows the box, not its users, so a seat has one before anybody is bound, which is exactly what a greeter needs. Your SDDM/GDM/greetd binding reads this one neutral flag; the contract names no display server and no session type.

B. What each person may do

Affordances are function arguments, not options — they ride the bind, at the one site that already names the user. There is no host-wide default for a bind to inherit, which is deliberate: giving one account sudo and another none is the same one mechanism written twice.

Function / argumentTypeDefaultWhat it means
bindContractUsers→ a NixOS module A host's whole user list, in one call. It adds no rule of its own — each entry is a bindContractUser, and the merge is the module system's. What it removes is the repetition.
 sourceflake / attrsetnull Whatever publishes contractUsers.<system>.<user>. Not called usersFlake because nothing requires a flake.
 users{ <name> = { <feature> = bool; source ? …; }; }{ } One entry per person. The key does selection, not naming — the account's name comes from the user's own identity.json, and the producer refuses to publish a user whose key and identity disagree. An entry may be empty. source is a per-user override of the default.
 allboolfalse Bind every user the default source publishes. Off by default and deliberately so: a users repo holds accounts that belong on some machines and not others, and binding them everywhere by omission is invisible until it matters.
bindContractUser{ source; username; affordances ? { } }— The singular underneath. affordances is { <feature> = bool; }, typed against the registry by hand rather than by the module system — an unknown feature name is a typo in the host's own repo, and must not silently become “affords nothing”.

C. The account schema — written by a bind, never by an operator

These options exist so that a bind has somewhere to write. An operator never sets them. The identity in particular is held, not authored: a second definition is an eval error rather than a merge — which matters because trustedKeys is a list, and lists merge by concatenation, so without that posture a second module naming the same user could append an SSH key to a realized account with nothing to notice.

OptionTypeWritten byWhat it means
contract.users.<u>.identitythe identity schemathe bindheld Carried straight out of the binding index.
contract.users.<u>.granted.<f>bool, one per featurethe bindThe grant seen as an option path. granted is never an argument; affordances is never an option.
contract.users.<u>.modeenum [ cli gui ]the bindcli The session shape this account was bound in — the account needs it, because a graphical session's input groups ride the mode rather than a grant.

D. The bindings a host supplies

The contract ships generic mechanism; the host supplies only bindings. That split keeps every fleet from re-implementing — and drifting on — the security-critical parts. The bindings are: the display / desktop launch commands, the home builder, and the trust-tier policy. All three live in the greeter's option set.

06

The bind, and the selection

Where the two sides actually meet

A bind walks five steps. It infers system from the host's own pkgs; reads the user's entry out of the binding index; reads which modes this machine runs; selects the mode; and grants what it afforded. Note what is not in that list: anything about a display. A graphical session's input groups follow the selected mode, so an ordinary desktop user's bind carries no affordances at all.

The selection kernel

Both the declarative bind and the runtime greeter select through one kernel, so the two paths cannot come to different answers. No mode name appears in the algorithm — the floor is a parameter, because a literal would make the registry's own flag decorative. 

# runs      = the floor ∪ whatever the MACHINE declared
# published = the modes this user actually has a built home for, HERE, on this system

candidates = runs ∩ published
rich       = candidates − { floor }

if  candidates is empty  → REFUSE   # no mode is common to the host and the user
if  |rich| > 1           → REFUSE   # two rich modes: no ordering exists to break the tie
if  rich is non-empty    → rich[0]  # a rich mode always beats the floor
otherwise               → floor

The three refusals, and why each exists separately

Every refusal in this repository carries three things: the problem, the why, and the fix. That is not decoration — two of these failures look identical under tryEval, and telling them apart is the whole point, because they have different causes, different fixes and different owners.

Unknown affordance

Checked first, before anything else. A misspelled feature name would silently afford nothing, and the account would come up quietly less powerful than the host meant.

Matrix subtraction

A mode this host runs and this user runs in, which this system's home matrix took away. Nothing built the home — so without this guard, selection would quietly fall back to the floor and activate a terminal home on a graphical seat with no message at all. It reports before selection, deliberately, so the right cause is named.

No common mode

This user runs nothing this host runs. A mode is what a home is, so a mismatch is a refusal rather than a silently lesser home.

And one more, deeper down The coupling guard. A host may activate a home only if it actually runs the mode that home was built for — read from the frozen manifest, not inferred. Selection satisfies this by construction; the guard covers the internal path where the kernel is called directly. It is the mode rather than the grant, because a grant not conferred degrades silently by design, whereas a graphical home activated on a machine with no display is a worse answer than an error.
07

The account plan

One pure function, rendered by two adapters

Once a mode is selected and a grant is decided, one pure function turns (identity, grants, mode) into a neutral account record. realization.nix renders it into users.users at build time; the greeter's provision renders the same record at login. Two adapters, one rule — so the security-critical part cannot drift between the declarative path and the walk-up path.

Account fieldComes from
descriptionthe identity's display name (GECOS)
hashedPasswordthe login credential, carried verbatim
authorizedKeysthe primary sshKey (dropped when empty), then trustedKeys, in that order
extraGroupswhat the MODE needs ∪ what the GRANT confers. There is no third source.
Try it · the account plan Two group sources meet in one union. Watch where privilege can and cannot enter.
The mode it was bound in

A mode's groups are non-privileged by construction — a mode is a capability, never a power. They still run through the privileged filter anyway, which is not vestigial: it is the one line stopping a privileged name added to modes.nix from reaching every account in that mode with no grant.

What the host afforded

Stated at the bind, on the line that already names the person. There is no host-wide default to inherit and no user-side veto to negotiate with.

Resulting account
description Ada Reference
hashedPassword $y$j9T$…
authorizedKeys [ ssh-ed25519 … ]
extraGroups
Where privilege can enter — and where it cannot

Powers route through grants, never raw identity. An identity cannot name a group at all, so the realization has no untrusted-input story to tell and no self-escalation route to close. And every grant rides the bind, over whatever home already exists — so a grant can never change a home, and one home serves granted and ungranted alike, for every feature without exception.

08

The greeter — the walk-up path

A flake URL, a username, a password

nixosModules.greeter is the reference runtime login path. It is opt-in per seat — a headless host simply never enables it, which is incapacity, not a ban — and it is replaceable, as long as a replacement honours the ordering below and confers at most the safe set.

Its governing discipline is data before code: authenticate on inert data before any of the user's Nix is evaluated. Eval is not a sandbox.

1
Promptreplaceable UI

A flake URL, a username and a password. Nothing about this person is declared on this machine.

2
Archive the sourceno user Nix yet

nix flake archive fetches the repo and its input closure. Still nothing evaluated.

3
Authenticate, eval-freethe crux of the ordering

jq reads identity.json directly: the password, and the Tier-1 signature over the repo. No Nix has run.

4
Classify the tierhost policy

tier1 — signed by a host-trusted key, home persisted, restricted eval. tier2 is designed-for but deferred, and refused by name rather than silently downgraded.

5
Select the modethe same kernel as a bind

Read the user's published modes off the flake's binding index with one cheap nix eval, and intersect them with what this seat runs. The selected mode's own parameters — gui.desktop — are read the same way, off modeParams — frozen to a store file at build time, so a seat with no display cannot claim to offer a desktop.

6
Build the homehost binding

The host's homeBuilder is invoked as homeBuilder <src> <username> <mode>, under the pinned restricted-eval posture. The mode is the greeter's answer, not the binding's — a seat never hardcodes one.

7
Provisionthe runtime realization

Fully realize the account from the identity plus the safe-set grant, and activate the home. This is the shell-side equivalent of realization.nix, rendering the same account plan — so a greeter user realizes identically to a build-time one, modulo a greeter-users seat marker.

8
Launch the sessionthe user's own choice

Map the desktop read at step 5 to one of the seat's offered desktops, and exec that command — exactly as a display manager would. An un-offered or empty name degrades to defaultDesktop, never a failed login.

The producer surface

How a users repo bakes a fleet of homes

The other half of lib. A host binds; a producer bakes. The producer's job is to build every member for every mode its system can run and the user runs in, and to publish the result as plain data.

a users repo's flake.nix
fleet = contract.lib.mkContractFleet {
  members    = contract.lib.mkMembers { usersDir = ./users; };
  homeMatrix = contract.lib.mkHomeMatrix {
    systems = {
      x86_64-linux      = { };        # `{ }` = every mode; a row states only what it takes AWAY
      aarch64-linux.gui = false;    # a headless builder tier
    };
  };
  pkgsFor       = sys: nixpkgs.legacyPackages.${sys};
  defaultSystem = "x86_64-linux";
  buildHome     = { member, mode, pkgs }: contract.lib.mkContractHome {
    inherit member mode pkgs;
    homeManagerConfiguration = home-manager.lib.homeManagerConfiguration;
    stateVersion = "25.11";
  };
};
# → inherit (fleet) homes homeConfigurations packages contractUsers;
FunctionTakesGives
mkMembers{ usersDir }{ <name> = { name; dir; identity; declaration; }; } — the repo's one answer to who is here and what does each say. A directory holding no member is a named error, never an empty set that bakes nothing while every output stays green.
mkHomeMatrix{ systems }{ <system> = [ <mode> ]; } — declared as subtraction, because an under-bake is silent. A contract that gains a mode bakes it everywhere with no consumer edit.
mkContractFleet{ members; homeMatrix; pkgsFor; buildHome; defaultSystem ? null }{ homes; homeConfigurations; packages; contractUsers; systems; pkgsBySystem; } — every output already nested by system. It instantiates pkgs once per system, never once per user.

mkContractUsers		{ pkgs; member(s); homes }The published package + index entry, for when your build is not every member × every mode.

Publication What a system publishes for a user is that system's matrix row ∩ the modes that user runs in. The fold intersects before it builds, so a home nobody could bind is never built. A system baking none of a user's modes publishes an empty index entry there rather than refusing — the matrix is fail-open on coverage, and the refusal belongs at the bind, where both sides can be named.

The CLI adapter

homeConfigurations.<user>-<mode> is the flat shape home-manager switch --flake .#ada-gui resolves. Nothing in the contract reads it — a host binds through the index and a greeter builds homes. The flat naming is not a repo's choice: home-manager's CLI quotes the fragment before it reaches Nix, so no nested spelling resolves. Being external and identical for every users repo is precisely why it has one owner rather than a fold per repo.

10

What actually crosses the seam

The binding index, the contractPackage, the manifest

Everything a host needs to know about a user is plain data. A host selects by reading, never by building every home to inspect what came out.

binding index

contractUsers.<system>.<user>
= { identity; modes; modeParams;
    contractPackages }

modes is carried as well as contractPackages precisely so the matrix-subtraction guard has something to compare against. modeParams carries each mode's own knobs, so a seat learns a user's desktop without building or opening a home.

contractPackage

What a producer publishes per home: the activation script plus a contract-manifest.json sidecar.

One package per mode, because a home is identified by the mode it was built for.

the manifest

Freezes exactly four fields:
{ version, username, packages, mode }

The mode is there because it is the one thing about a home a bind cannot change — and therefore the one thing worth asserting about.

Versioning and compatibility

Compatibility is by major version. A contractPackage a users repo published keeps binding on a host that has moved on — until a major release, which is refused by name with a message explaining that the agreement itself changed. Pre-1.0 the minor plays the major's part, so 0.3.1 and 0.3.9 are compatible while 0.4.0 is not.

Keeping inputs.users.inputs.contract.follows = "contract" in the host's flake sidesteps the question entirely: both sides are then the same contract, by construction.

Activation, on the host

A bind installs a systemd oneshot — not an activationScript — because activation must run after PAM is configured. It executes the home's activate inside a real login session (runuser -l), which is what a genuine home-manager activation needs for its sd-switch step: a running user systemd manager and an XDG_RUNTIME_DIR. The account is set to linger, so the home's user services keep running after activation exits. If allowedPrograms is non-empty, a second step then replaces ~/.nix-profile with the host-built policy profile.

11

Proving it

Three surfaces, three kinds of evidence

The contract ships three distinct surfaces, answering three different questions. lib is the contract's own functions. The check kit, inside lib, hands a consumer the technique for proving a claim about its own repo — the contract hands over the technique, never the verdict. testing hands over a machine: it boots a seat host, and the claim stays the caller's to write.

The check kit — proofs only a consumer can run

CheckProves
mkConfinementCheckYour real module set has no system channel — positive control included.
mkIdentityPostureCheckEvery identity.json carries the hash strength you chose. Consumer-owned and opt-in, because a private repo may legitimately ship $6$ while a public one needs memory-hard $y$. The loader imposes none.
mkHomeEvalCheckEvery home you build evaluates, on every system you build for.
mkMemberChecksAll three, across every member, in one call. Use the adapter unless your fleet builds different members on different systems — a hand-listed check set always misses the member somebody forgot to add, and a missing check reads exactly like a passing one.
mkClaimReportNothing — it reports. Runs your named claims, prints an ok/FAIL line each, threads in proofs whose being built is the verdict, and fails the build if anything failed. An empty claim list is refused: a report folded over nothing prints a header and passes.
mkProofPreludeThe shell an execution proof opens with — a fail <message> that names the proof on stderr and exits non-zero.

The seat harness

testing.mkSeatHarness gives a consumer the boot base, the greeter preamble and greetd wiring, and the fixtures a seat test varies against. It is what the contract's own runtime proofs are built on — published so that a consumer's VM test binds that same harness rather than re-authoring a seat host free to drift from it.

Running everything

“Run everything” is three targets, because the two reference fleets carry their own checks — they need home-manager, which the contract deliberately does not input. Nothing but running all three catches drift between them. 

nix flake check .                # the contract: synthetic conformance + runtime VM tests
nix flake check ./examples/users # the reference users repo
nix flake check ./examples/fleet # the reference host repo
The conformance suite

Adversarial synthetic worlds probing the decision logic — proving the filter drops and the guard fires. No host repo, no home-manager. It borrows real atoms from the reference fleets, never the reverse.

The runtime VMs

Booted NixOS VMs proving what eval cannot show: that the display surface renders, that a greeter login materialises a real account and activates a real home, that the full archive → auth → build → provision → session loop runs end to end, and that a real Plasma desktop comes up the way a display manager would exec it.

The laws

Every one of these is enforced somewhere, not merely intended
01
A user is self-contained.Identity, declaration and home all live in the user's own directory. Lifting one user out into their own repo is a directory move. No host may own a user's credentials.
02
A grant can never change a home.A home is built ahead of time and sealed. One home serves granted and ungranted alike, for every feature without exception — there is no per-feature flag saying otherwise.
03
An identity describes a person, never their powers.An account's groups come from exactly two places, and both are decisions somebody else made: the session it was bound in, and what the host afforded.
04
The two registries touch nowhere.No entry in modes.nix names a feature; no entry in features.nix names a mode. No value crosses between them.
05
Incapacity, not a ban.A headless host does not refuse a desktop, it cannot run one. That is why contract.modes and affordances are different mechanisms in different places.
06
Data before code.A greeter authenticates on inert data before any of the user's Nix is evaluated. Eval is not a sandbox.
07
No secrets beyond the login credential.A one-way hashedPassword and public keys. A user's own home secrets ride the user's own key, provisioned by the user's own home module — never through the contract.
08
The runtime evaluates the same kernels.Selection and the account plan each have exactly one implementation, executed at build time and at login. A rule with two spellings is a rule with two behaviours.
09
One option prefix per party.Everything is under contract.*, on both eval-sides. There is no second prefix and none per party.
10
Mechanism from the contract, bindings from the host.The display launch, the home builder, the trust policy are the host's. Everything security-critical is the contract's, so no fleet re-implements it and drifts.
11
The contract depends on nothing but nixpkgs lib.No home-manager, no packages. That is what lets a greeter re-import the kit at login with only lib in hand, and what forces the reference fleets to carry their own checks.
12
Fail-closed on capability, fail-open on coverage.A host that says nothing runs only the floor. A matrix row that says nothing bakes everything. Fail-closed where the risk of the unknown is admitting something; fail-open where the risk is omitting it.
